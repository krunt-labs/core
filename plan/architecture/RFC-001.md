# 1. Abstract

Krunt is a backend builder for visually authoring deterministic software systems,
built on Graph Giraffe, the underlying domain-agnostic node editor library.

Rather than acting as a low-code application builder, Krunt introduces a
graph-native programming model where visual graphs are treated as source code.

The editor itself is intentionally domain-agnostic.

Every domain—including backend systems, AI workflows, rendering pipelines, ETL pipelines, state machines, and infrastructure—is implemented as a semantic layer built on top of a common graph model.

---

# 2. Motivation

Most node editors tightly couple:

- editor
- execution
- runtime
- domain

into one implementation.

Examples include:

- Blueprint systems
- Shader editors
- Workflow builders
- Backend builders

This makes them difficult to extend beyond their original purpose.

Krunt and Graph Giraffe separate concerns into independent layers.

The editor understands graphs.

The compiler understands semantics.

The runtime understands execution.

This separation enables the same graph infrastructure to compile into entirely different domains.

---

# 3. Goals

The platform MUST:

- provide deterministic compilation
- support multiple semantic domains
- separate execution flow from data flow
- support compile-time validation
- support plugins
- support AI-assisted authoring
- remain framework independent
- generate production-grade artifacts

---

# 4. Non Goals

The platform SHALL NOT:

- execute arbitrary JavaScript inside graphs
- use AI for correctness
- be framework specific
- become a visual scripting language
- sacrifice determinism

# 30. Krunt Implementation Decisions

Krunt is the first backend product built on the Graph Giraffe node editor. These decisions
refine the platform architecture for its initial implementation and supersede
the narrower TypeScript-only assumptions in the Backend Tool PRD where they
conflict.

## 30.1 Multi-target backend architecture

Krunt supports multiple language and framework targets from the beginning. The
first implementation is TypeScript with NestJS.

The target pipeline is:

```text
Backend graph
    ↓
Universal semantic IR
    ↓
Language backend (TypeScript first)
    ↓
Framework backend (NestJS first)
    ↓
Generated project
```

The universal IR SHALL contain no framework imports, filenames, or framework
idioms. Language backends lower universal IR into language-specific IR.
Framework backends lower language IR into a target contract and generated
artifacts. Express, PHP/Laravel, and other targets can be added without
changing the graph model or universal semantic IR.

## 30.2 Initial editor strategy

Krunt initially uses React Flow as an internal editor renderer to accelerate
product development. React Flow nodes and edges are projections, not the
compiler source format.

The canonical relationship is:

```text
Krunt graph document → editor adapter → React Flow
Krunt graph document → editor adapter → Graph Giraffe (later)
```

The editor adapter owns projection, commands, interaction events, diagnostic
rendering, and presentation state. The compiler owns structural and semantic
validation. Graph Giraffe remains the long-term renderer candidate and must
consume the same canonical fixtures before substitution.

## 30.3 Evaluation model

Execution edges are push-controlled: an entry point activates downstream
control flow. Data dependencies are resolved pull-oriented within that active
execution: an operation requests the values required by its inputs. Async
values are explicit in the type and IR systems. Streaming and event-driven
features may introduce push-based data semantics later.

Arbitrary execution cycles are invalid. Structured cycles are represented by a
dedicated `Loop` construct. Recursion is deferred until subgraph invocation
semantics are defined.

## 30.4 Compilation failure policy and traceability

Error-severity diagnostics block lowering and generation. Compilation SHALL
return structured diagnostics with stable codes, severity, compiler stage,
primary graph element ID, related element IDs, and optional structured help.

Source mappings SHALL be preserved from graph nodes, ports, and edges through
universal IR, language IR, and generated artifacts. AI-authored graphs follow
the same validation and failure path as manually authored graphs.

## 30.5 Editor layer organization

Krunt’s layer pane contains broad backend topics rather than one section per
node type. Examples include Authentication, Routing, Persistence, Caching,
Storage, Communication, and Observability. Each topic may contain related
stateless/stateful or concrete node types.

The layer pane is product/editor presentation metadata. It must not introduce
backend semantics into the domain-neutral graph editor or structural graph
model.

## 30.6 Sandbox boundary

Sandboxing is deferred from the initial compiler. Future work may sandbox
generated-backend preview and testing with explicit network, filesystem,
database, secret, CPU, memory, and time capabilities.

Plugin sandboxing, generated-application sandboxing, and graph preview
sandboxing are separate concerns. The compiler SHALL remain side-effect free
and SHALL NOT execute arbitrary graph-provided JavaScript.

## 30.7 Canonical graph requirements

The Krunt graph document SHALL provide explicit semantic ports rather than
relying on visual handle sides. Edges SHALL identify their source and target
ports and declare whether they represent execution flow or typed data flow.

Editor snapshots may contain camera, theme, texture, and layout state, but those
fields SHALL remain separate from executable graph semantics. Graph documents
must include graph schema, plugin, semantic, and compiler version metadata and
support deterministic serialization and migrations.
